# IMP-1: импорт банковской выписки без потери состояния

Спека, по которой писался клиент. Писалась до кода; пункты приёмки связаны с тестами. Источник требований: ТЗ и `kit/README.md` (контракт mock).

## Цель
Клиент на React Native и TypeScript (Expo SDK 54, development build): выбрать PDF или CSV системным picker,
проверить на устройстве, отправить реальные байты в mock, отследить job, пережить потерю ответа и перезапуск,
безопасно удалить импорт. Нативный запуск на iOS-симуляторе и Android-эмуляторе.

## Договорённости до начала
- Expo dev build (`expo prebuild`, `expo run:*`), `ios/` и `android/` не коммитятся.
- `kit/` не меняется.
- Интерфейс на английском; README, release note, self-review на русском.

## Решения по ходу
- Expo SDK 54 (RN 0.81) вместо последней версии: SDK 55–58 требуют Xcode новее установленного 26.0.1.
- Android NDK стандартный для React Native 0.81. Локально собиралось на установленном 27.0.12077973, вписанном в сгенерированный `android/build.gradle`: на загрузку другой версии не было места.
- Загрузка через `uploadAsync` из `expo-file-system/legacy` (`BINARY_CONTENT`, `FOREGROUND`): в SDK 54 у `File` нет `upload()`. `FOREGROUND` выбран, чтобы фоновая сессия iOS не досылала файл после того, как экран показал «не подтверждено».
- Тесты на Jest с babel-preset-expo в окружении node (ядро без RN); `jest-expo` не нужен.
- Отступление от TDD: валидатор (`validate.ts`) написан до `validate.test.ts`, его тесты сразу были зелёными. Интеграционные тесты были красными до контроллера.

## Решения по дизайну
- Ядро без зависимостей от RN (`app/src/core/*`): проверка байтов, контроллер операции, запросы через `fetch` с таймаутом 15 с.
  Нативный слой (`app/src/native/*`): picker, приватная копия, загрузка через `uploadAsync` без чтения файла в память JS.
- Проверка файла: сначала размер по метаданным picker, затем нативная копия в приватный cache, затем размер копии, затем первые байты (`%PDF-` или заголовок CSV, как в mock). Расширение и MIME не используются.
- Ключ идемпотентности и минимальная запись операции сохраняются до POST. При сетевом сбое POST операция переходит в `unknown`, автоматически идёт только `GET by-key`. Повторный POST только по кнопке, тем же ключом и с той же копией.
- Каждый ответ сверяется с операцией, для которой ушёл запрос: ключ идемпотентности и фаза ожидания job для POST и `by-key`, `jobId` для GET, ключ удаления для DELETE. Ответ для операции, с которой пользователь уже ушёл, отбрасывается.
- Ревизии: состояние job принимается только при `revision` строго больше текущей. Исключение: после перезапуска та же ревизия принимается один раз, чтобы получить отчёт, который не сохраняется на диск.
- Удаление: ключ удаления сохраняется до DELETE. «Удалено» только после GET со статусом `deleted`; тело ответа DELETE этого не доказывает. 503 даёт «не удалено». Потерянный ответ даёт «удаление не подтверждено», повтор идёт тем же ключом. 404 на DELETE даёт отдельное состояние `not_on_server`.
- Уход с операции, которая может остаться на сервере (`unknown`, `delete_failed`), только после подтверждения пользователя.
- Приватная копия удаляется при отмене, при отказе, после подтверждения job сервером; при старте удаляются оставшиеся копии. Копия picker (Android `cache/DocumentPicker`, iOS `tmp/<bundle>-Inbox`) удаляется сразу после проверки файла и при старте.
- Файл операции хранит фазу, ключи, код ошибки, `jobId`, статус, ревизию и, до подтверждения загрузки, путь, размер и формат копии. Имени файла и отчёта в нём нет.
- Логи содержат только тип события, `jobId`, статус, ревизию, HTTP-код. Имени файла, байтов и описаний операций в них нет.
- Повторный POST после 404 по ключу только вручную: сервер мог ещё не дописать job, автоматический повтор рискует дублем.
- Переключатели mock и журнал «What the app is doing» есть только в `__DEV__`-сборке.

## Приёмка
Тесты: `app/__tests__/` (Jest, интеграция против `createMockServer` из `kit/`).

1. Ключ идемпотентности сохранён в хранилище до первого POST. — `import-flow.test.ts › persists key before POST`
2. happy: реальные байты отправлены (`acceptedBytes` равен размеру фикстуры), 202 показан как `queued`, а не как отчёт; после ready 2 позиции, итог 151.99 AUD в месяц. — `› happy`
3. lost_ack: один job (`newJobs=1`); восстановление по ключу без повторного POST; после перезапуска (новый контроллер из хранилища) тот же job, `createRequests` не растёт. — `› lost_ack`
4. Неподтверждённый POST и недоступный `by-key`: ручной повтор тем же ключом даёт тот же job (`newJobs=1`, `duplicateHits=1`). Перезапуск с неотправленным ключом: 404, без автоматического POST; ручной повтор после этого уходит с тем же ключом. — `› manual retry`, `› relaunch with an unsent key`
5. stale_status: после ready/r3 ответ processing/r2 не откатывает состояние. — `› stale_status`
6. delete_failure: 503 даёт «не удалено», статус job не `deleted`; после `happy` повтор тем же ключом доходит до `deleted`. — `› delete_failure`
7. Поздний ответ (ready/r3) после deleting/deleted не воскрешает job. — `› late response`
8. spoofed.pdf и файл больше 10 МиБ отклонены до POST; `createRequests` до и после равны. — `› rejects spoofed and oversize files before POST`
9. statement.csv и statement.pdf принимаются валидатором. — `validate.test.ts`
10. Логгер не получает имя файла, байты и описания операций. — `› logs`
11. Ручная нативная проверка на iOS и Android: picker, полный импорт, сценарии сбоя, крупный шрифт, маленький экран. — README, раздел «Результаты проверки». Маленький экран и крупный шрифт на Android не проверены.
12. Сброс во время восстановления по ключу не воскрешает job, новый выбранный файл остаётся. Поздний 404 по ключу не перезаписывает новый выбранный файл. — `› discard during an in-flight recover`, `› late by-key 404`
13. «Check again» одновременно с восстановлением при запуске даёт один job и одно удаление копии. — `› Check again racing the launch recover`
14. Поздний 404 после `deleted` не превращает экран в «Import failed». — `› late 404 after deleted`
15. Потерянный ответ на DELETE даёт «удаление не подтверждено», повтор тем же ключом доходит до `deleted`. — `› lost DELETE response`
16. Тело DELETE со статусом `deleted` без подтверждения GET не даёт «удалено». — `› DELETE body alone does not mark deleted`
17. DELETE 404 даёт отдельное состояние `not_on_server`. — `› DELETE 404`
18. Файл операции без имени файла и отчёта; после перезапуска отчёт читается заново. — `› stored operation keeps no file name or report`
19. Зависший запрос прерывается по таймауту. — `› a hanging request times out`
20. Размеры показываются в KiB и MiB. — `strings.test.ts`
21. Журнал диагностики показывает потерянный POST и поиск по ключу, отброшенный старый статус, 503 на удаление и повтор; имени файла в нём нет. — `dev-log.test.ts`

Тест: п. 4 — тест перезапуска с неотправленным ключом расширен: файл в хранилище теперь без имени (так его сохраняет приложение), добавлен ручной повтор. Проверка «нет автоматического POST» не изменилась.
Тест: п. 3, 4 — тестовые хранилище и транспорт перешли на тип сохраняемой записи `StoredOperation`; добавлен помощник `holdFetch` для поздних ответов. Смысл проверок не изменился.
